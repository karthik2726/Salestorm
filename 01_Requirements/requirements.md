# SALESTORM System Requirements & Architecture Constraints

## 1. Functional Requirements (FR)

The SALESTORM platform automates high-concurrency flash-sale execution across a 12-stage e-commerce lifecycle pipeline.

```
[1. Discovery] ──> [2. Cart] ──> [3. Admission] ──> [4. Inventory Reservation]
                                                               │
[8. Fulfilment] <── [7. Order Creation] <── [6. Payment] <─────┴── [5. Checkout]
       │
       ├──> [9. Shipment] ──> [11. Delivery Tracking]
       └──> [10. Notification] ──> [12. Expiry Sweeper]
```

| ID | Pipeline Stage | Functional Requirement Description |
| :--- | :--- | :--- |
| **FR-1** | Product Discovery | The system shall serve static product catalog pages and real-time availability flags directly from edge CDN cache without hitting core database clusters during high-traffic events. |
| **FR-2** | Cart Service | The system shall maintain transient cart states for authenticated users, generating a cryptographically signed checkout payload containing product IDs, quantities, and price snapshots. |
| **FR-3** | Inventory Check & Admission | The system shall enforce a virtual waiting room and token-bucket admission control at the edge/gateway layer, throttling ingress traffic to match down-stream Reservation Service processing capacity. |
| **FR-4** | Inventory Reservation | The system shall atomically validate customer purchasing eligibility (max 1 unit/user), verify stock availability, decrement stock in-memory, and issue a 10-minute reservation token. |
| **FR-5** | Checkout | The system shall create a pending checkout session bound to a valid reservation token and an idempotency key generated by the client device. |
| **FR-6** | Payment Processing | The system shall process payments through external gateway adapters using idempotency keys (`reservation_id`). It must handle timeouts, circuit breaking, and transition indeterminate transactions to `PAYMENT_UNKNOWN`. |
| **FR-7** | Order Creation | The system shall asynchronously construct orders via the Transactional Outbox pattern upon receipt of a verified `PaymentConfirmed` event. It must maintain durability across service outages (e.g., 30s Order Service downtime). |
| **FR-8** | Fulfilment | The system shall mark reserved inventory as `SOLD` in PostgreSQL and trigger warehouse allocation workflows upon order confirmation. |
| **FR-9** | Shipment | The system shall generate dispatch labels asynchronously via external courier logistics APIs once order confirmation is persisted. |
| **FR-10** | Notification | The system shall publish push/email/SMS notifications to customers at key lifecycle events (`RESERVED`, `PAYMENT_RECEIVED`, `ORDER_CONFIRMED`, `SHIPPED`). |
| **FR-11** | Delivery Tracking | The system shall ingest logistics carrier webhooks to update shipment status (`IN_TRANSIT`, `OUT_FOR_DELIVERY`, `DELIVERED`). |
| **FR-12** | Reservation Expiry & Compensation | The system shall execute background reconciliation and sweeper jobs to release inventory reservations that exceed the 10-minute TTL or fail payment, returning stock to the available pool atomically. |

## 2. Non-Functional Requirements (NFR)

### 2.1 Throughput & Capacity Targets
* **Normal Operating Ingress:** 10,000 requests per second (req/s).
* **Flash Sale Peak Ingress (Edge):** 500,000 req/s.
* **Core Core Admission Ingress:** Throttled to 10,000 req/s max at API Gateway.
* **Sustained Database Write Throughput:** 2,500 write transactions/sec (PostgreSQL primary).

### 2.2 Latency SLAs (Targeted Metrics)

| Endpoint / Operation | HTTP Method / Protocol | Target p95 Latency | Target p99 Latency |
| :--- | :--- | :--- | :--- |
| Static Catalog & Sale Status | `GET /api/v1/products/{id}` | < 10 ms (Edge Cache) | < 25 ms |
| Virtual Waiting Room Poll | `GET /api/v1/queue/status` | < 15 ms | < 35 ms |
| Inventory Reservation | `POST /api/v1/reservations` | < 20 ms | < 50 ms |
| Checkout Session Creation | `POST /api/v1/checkout` | < 45 ms | < 90 ms |
| Payment Gateway Execution | `POST /api/v1/payments` | < 800 ms (Gateway bound)| < 2,000 ms |
| Async Order Event Processing | Kafka Event Processing | < 30 ms | < 100 ms |

### 2.3 Availability & Resilience
* **Availability Target:** 99.99% overall uptime (< 52.6 minutes unexpected downtime per year).
* **Isolation Guarantee:** Faults in Notification, Courier Logistics, or Order Service processing shall not crash or block the core Inventory Reservation and Payment capture pipelines.

### 2.4 Data Consistency & Durability
* **Inventory Decrement:** Strict Linearizability (zero oversell, zero double-reservation).
* **Order Processing:** Eventual Consistency bounded within < 2,000 ms under normal conditions.
* **Recovery Point Objective (RPO):** RPO = 0 for financial and inventory database transactions (synchronous WAL replication to standby).
* **Recovery Time Objective (RTO):** RTO < 30 seconds for automatic database primary failover.

### 2.5 Security & Compliance
* **Transport & Storage:** TLS 1.3 in transit; AES-256 for database and Redis storage at rest.
* **Authentication:** Stateless OAuth2 JWT tokens validated at the API Gateway.
* **Payment Security:** Full PCI-DSS compliance by delegating direct card handling to tokenized gateway adapters.

## 3. Traffic Math & Admission Filtering Pipeline

### 3.1 Scenario Parameters
* **Target Product X Stock:** $N_{stock} = 100$ units.
* **Total Flash Sale Buyers:** $U = 10,000$ concurrent buyers clicking "Buy Now" simultaneously ($t = 0$).
* **Peak Burst Rate at Edge:** 500,000 req/s (accounting for retry loops, bot activity, page refreshes).

### 3.2 Ingress Filtering Math

```
500,000 Edge req/s
  │
  ├─> [WAF & Rate Limiter] ──(Rejects 400,000 req/s: Bots/DDoS)──> HTTP 429
  │
  ├─> [Edge CDN SOLD_OUT Gate] ──(Rejects 90,000 req/s post stock depletion)──> HTTP 200 "Sold Out"
  │
  └─> [Virtual Waiting Room (Leaky Bucket)] ──(Admits 10,000 req total @ 100 req/s rate)
        │
        └─> [Core Reservation Service (Redis Lua Gate)]
              │
              ├──> 100 Successful Reservations (Stock = 0) ──> SOLD_OUT flag pushed to Edge
              └──> 9,900 Rejections (Stock Exhausted) ──> HTTP 409 "Out of Stock"
```

1. **Edge WAF & IP Rate Limiting:**
   Drops 80% of illegitimate traffic ($400,000\text{ req/s}$) prior to hitting application infrastructure.
2. **Virtual Waiting Room (Queue Rate Admission):**
   Caps admission to the backend core at $100\text{ req/s}$. The $10,000$ genuine buyers enter the waiting queue.
3. **Core Inventory Reservation (Redis Atomic Gate):**
   * First 100 requests acquire reservations within $t = 1.0\text{ sec}$.
   * Inventory counter reaches $0$. Redis issues an event pushing `SOLD_OUT = true` flag to Cloudflare/Fastly CDN KV storage within $< 200\text{ ms}$.
4. **CDN Edge Dropping:**
   Subsequent incoming requests from the waiting room or client refreshes hit the CDN edge cache and receive an immediate HTTP 200 "Sold Out" static page response, completely shielding core microservices from remaining load.

## 4. Strict Guarantees vs. System Targets

| System Aspect | Category | Exact Operational Specification | Failure Mitigation Mechanism |
| :--- | :--- | :--- | :--- |
| **No Oversell** | **STRICT GUARANTEE** | Available quantity of Product X shall NEVER fall below zero ($available\_quantity \ge 0$). | PostgreSQL `CHECK` constraint + Redis Lua atomic check & decrement. |
| **No Double-Reservation** | **STRICT GUARANTEE** | A customer ($customer\_id$) can reserve at most 1 unit of Product X per sale event. | Unique index `(sale_id, customer_id)` in DB & SETNX in Redis. |
| **No Double-Charge** | **STRICT GUARANTEE** | External Payment Gateway shall never execute more than 1 successful charge per reservation. | Unique `idempotency_key` mapped directly to `reservation_id`. |
| **No Duplicate Order** | **STRICT GUARANTEE** | Exactly one Order entity created per successful payment transaction. | DB Unique Constraint on `payment_id` / `reservation_id` + Consumer Idempotency Table. |
| **System Latency** | **SYSTEM TARGET** | p95 latency < 20ms for reservation gate under 10k req/s ingress. | Throttling via Waiting Room + Redis in-memory execution. |
| **High Availability** | **SYSTEM TARGET** | 99.99% operational uptime across microservices. | Multi-AZ Kubernetes pods + DB Read Replicas + Kafka durability. |
| **Notification Speed**| **SYSTEM TARGET** | Email/SMS sent within 5 seconds of order creation. | Asynchronous decoupled Kafka consumers. |

## 5. System Architectural Trade-Offs

1. **Dual-Datastore Inventory Model (Redis + PostgreSQL):**
   * *Sacrifice:* Data duplication and risk of transient state divergence during abnormal Redis master crashes.
   * *Justification:* PostgreSQL cannot handle 500,000 req/s lock contention on a single row without severe connection pool exhaustion and transaction timeouts. Redis handles 100k+ ops/sec per node in memory.
   * *Mitigation:* Background reconciliation service continuously syncs and reconciles Redis reservations against DB WAL records.
2. **Asynchronous Order Creation (Kafka Outbox Pattern):**
   * *Sacrifice:* Immediate synchronous feedback of order creation to the buyer. User sees "Payment Received - Confirming Order" for 1-2 seconds.
   * *Justification:* Decouples Payment Service from Order Service. Allows system to absorb complete 30-second Order Service outages without dropping transactions or failing payments.
3. **Edge Throttling & Waiting Room:**
   * *Sacrifice:* Real-time user experience for long-waiters who ultimately receive a "Sold Out" notification.
   * *Justification:* Prevents cascading failure of core database and API gateway under extreme load spikes.
